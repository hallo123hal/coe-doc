## 2. Auto SKU creation on Hybris from AEM
- AEM-created SKUs flow into Hybris via cronjob `xx-DotComCmsDeltaProductSyncJob` (toko config `toko.create.categories.from.dotcom`, `toko.create.products.from.dotcom`) and are not yet sold, so they have no ticket. A daily "Updated Products Report" email lists them (raise a ticket to be on the recipient list).
- AEM only sends base SKU, SKU and AEM category; product type defaults to Normal. CoE completes: correct Hybris category added as supercategory (never remove existing ones; e.g. Thailand dryer AEM 08010300 + DA0203), Required Additional Info, Super Sync for NERP data, external service type, country delivery modes, sales unit "pieces". The subsidiary later raises a ticket to activate the SKU. Use the Category Structure page when AEM categories change.

## 3. Z-code
- Custom product (usually non-Samsung) for promotions, e.g. cash/retail vouchers, power banks; not in AEM. Product types: NORMAL (in NERP), GHOST_PRODUCT (no physical item/free gift, not in NERP), NON_SAMSUNG (digital/physical, NERP depends on subsidiary), EXTERNAL_SERVICE_SKU (SC+, CE packcode, T-code), PLACEHOLDER_PRODUCT (Galaxy Ring placeholder).
- Standardisation by country: base code (e.g. MY `Z-SME`/`Z-INSTALL`, ID `IDFREEBIE-MX/CE/HA`, SG `SGFREEBIE`, VN/AU `Z-XXXX`, NZ `Z-NZ`), product type (Thailand forbids NON-SAMSUNG because it corrupts NERP posting; Indonesia forbids Normal), no Super Sync for any, delivery mode of the main device, RRP supplied by subsidiary (PH PHP 1, SG 0, ID must have an RRP). Warehouse and stock are mapped/entered manually; RRP changes need Knox pricing approval (RRP 0 reportedly approved up to the CEO); image supplied by the subsidiary and uploaded by CoE; PIN map required for Philippines.
- Indonesia has its own strict checklist (ID Estore/EPP/SME only, not 3PD; PURCHASABLE_NON_VISIBLE). Singapore uses ghost "shipping/freebie message" Z-codes (e.g. `Z-SHIPPING-NOTICE`, `Z-GIFT-REDEMPTION-MSG`, `Z-OUTOFSTOCK-MESSAGE`) that print notices on invoices; unsure cases need RHQ approval.
- Q&A: whether a SKU is in NERP must be confirmed by the subsidiary on the ticket (Jira is the source of truth; no confirmation, no execution). If it syncs from NERP, no manual change; if not in NERP, CoE sets price, warehouse, stock.

## 4. F-code (virtual bundle)
Binds two or more components into one sellable code (adding the F-code puts all SKUs in the cart); needs RRP, category and child SKUs linked via CONSISTS_OF and MASS_PURCHASE_WITH_COMPONENT references. Mostly Malaysian air conditioners; past examples TV + soundbar, phone + watch + buds. Docs: KB – F-code (virtual bundle) playbooks V3/V4 and TV + Freestyle. Bomb codes work similarly.

## 5. Super Sync
- Done in the Master Catalog via the Products Sync Selector Wizard (Product Cockpit); result must be SUCCESS (check Messages). New process: AEM-registered SKUs sync automatically.
- Warehouse/stock: never create warehouses by hand (come from NERP; exception external services such as SC+). Stock is overwritten by the NERP cronjob; overselling amount sells future stock (MX from NERP forecast); max pre-order only in flagship pre-order; never remove reserved amount (actual = available − reserved); forecast stock from GSCM (weeks 1–3) for MX in all subsidiaries except Vietnam (multi-warehouse); virtual/dummy stock for CE on request (block stock sync, then set amounts). GSCM forecast override (RTF) is covered in a later session.
- Price: Normal products' RRP must sync from NERP (including accessories/chargers); products not in NERP (SC+, P-code, Z-code, F-code) get RRP via bulk upload; manual RRP upload needs senior/lead and RHQ written confirmation; no RRP means no frontend display.
- Errors: warehouse/stock "no NERP response" → subsidiary checks NERP; RRP fail → NERP; DOTCOM fail → AEM. Standard tool is the Product Sync Selector (select 100 SKUs at once).
