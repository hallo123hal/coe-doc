# TEC-3.1 Order, fulfilment, payment, fraud, ERP

> Nguồn: page 2483388471 · 75 phút (Study 25' · Demo 10' · Quiz 10' · Practice 30') · Lecture + demo một order trên Backoffice staging + bài chẩn đoán order kẹt; facilitator: Tech Sub-Lead có L2 cho TEC-ORD · Cần xong G4.1, TEC-2.2, TEC-2.3; Backoffice + HAC staging (không có thì làm giấy và xem demo). Facilitator chọn trước 1 order staging có ≥2 consignment để cả lớp xem chung.

## Mục tiêu
Tìm OrderProcess, ConsignmentProcess và task log của order; chẩn đoán nguyên nhân 8 loại order kẹt và chọn đúng bước rerun; kiểm điều kiện an toàn trước rerun (CAPTURE, số NERP) và biết khi nào giao cho SDS India; tìm log tạo SO trong Kibana bằng đúng từ khóa.

## Thuật ngữ
**OrderProcess** (item business process gắn với một order, code `order-process-...`; mỗi consignment có **ConsignmentProcess** riêng); **ProcessState** (running, ERROR…; query "Pull Order - Order stuck" lọc ERROR); **Retrigger** (chạy lại process từ một step bằng `restartProcess` sau khi sửa nguyên nhân); **Retry-safe** (rerun không tạo trùng — không capture hai lần, không tạo SO thứ hai); **1st GI / 2nd GI** (Goods Issue trên NERP: 1st = hàng rời kho (movement 261), 2nd = khách nhận hàng (601)); **Billing** (chứng từ NERP tạo sau 2nd GI; order COMPLETED khi có billing number); **RSO, RDO** (Return Sales/Delivery Order); **MT_ESTORE_ORDER_CREATE_S/_R** (tag log Kibana: Hybris gửi PO (S) và nhận SO (R) từ NERP).

## Nội dung
### 1. Process điều khiển order
Merch/QA chỉ cần nhận biết order kẹt; Tech phải tìm đúng step đã dừng, sửa nguyên nhân và rerun process **với PC ticket**. Order đi qua các step của OrderProcess; sau `splitOrder` mỗi consignment chạy ConsignmentProcess riêng và OrderProcess chờ tất cả xong. Điều tra: mở order ở Backoffice xem Order process ("running" = chưa xong; ProcessState ERROR = lỗi); đọc task log để biết action nào dừng và message lỗi chính xác; tìm hàng loạt bằng query "Pull Order - Order stuck" (lọc OrderProcess/ConsignmentProcess có ProcessState ERROR).

### 2. Các step chính theo thứ tự
sendOrderAcknowledgementEmail → checkOrder → fraudCheck / fraudCheckExternal → reserveVirtualStock → processExternalServices → takePayment → sendFinancialUpdate (FI posting sang NERP) → isInitialFISuccess → splitOrder → waitForWarehouseSubprocessEnd → isFullyFulfilled → isSecondFIRequired → waitForFinancialCompletion → sendThankYouMessage. Bốn cặp phải giữ thứ tự: check order & fraud trước reserve stock; reserve stock trước capture; FI đầu tiên trước split; phần kho xong trước financial completion.

### 3. Chứng từ NERP và status order
Hybris gửi PO (số order Hybris), NERP trả SO; DO (Delivery Order) đi tới kho — Hybris nhận DO thì order sang SHIPPING_PREPARATION; nhận 1st GI thì SHIPPED; 2nd GI khi khách nhận hàng rồi NERP tạo Billing; Hybris nhận billing number thì COMPLETED. Return: RSO → RDO → return billing.

### 4. Tìm log tạo SO trong Kibana
Discover, index `logs-json-*`, đặt ngày Absolute. Order kẹt ORDER_SPLIT: tìm `"<order code>" AND "<soap"`; đọc cặp tag MT_ESTORE_ORDER_CREATE_S (Hybris gửi PO) và _R (NERP trả SO). Kibana giữ log ~3 tuần (thực tế 25–26 ngày; handover Kibana 28/10) → kiểm sớm. Thêm `logs.message` làm cột để đọc nội dung log.

### 5. Rerun đúng bước và chỉ khi an toàn
Rerun từ **step đã dừng**, không từ đầu (mọi lần chạy production cần PC). Ví dụ từ D2C COE Order Remediation: kẹt ORDER_SPLIT đã sửa nguyên nhân → rerun từ `isFulfilmentRequired`; kẹt SHIPPED dù consignment xong → chạy `isProcessCompleted`/`isFullyFulfilled`; SC+ sai PID, Kibana báo "INVALID BILL DATA" → sửa Manufacturer AID rồi rerun `processExternalServicesAction`; "minus value not permitted" ở WAITING_FOR_TRANSFER → chỉnh thuế theo xác nhận của subsidiary rồi rerun `waitForSendToWarehouse`; hủy return request → subsidiary xóa RSO/RDO trên NERP trước, rồi mới xóa trên Backoffice và chạy `isReturnRequestCancelling2`.
**Điều kiện an toàn trước rerun:** không đoán — payment status quyết định hủy hay đẩy tiếp, không chắc thì hỏi subsidiary bằng comment ticket; trước khi rerun `takePayment` nếu order đã có CAPTURE entry thì **không chạy** (tránh trừ tiền khách hai lần); nếu order đã có số NERP thì không đẩy lại, còn log cho thấy đã gửi mà không có số trả về thì rerun không retry-safe → giao SDS India qua Maintenance Request. Dữ liệu order process bị xóa sau **45 ngày** nên clawback trade-in cho order cũ hơn 45 ngày phải làm bằng script. Lỗi hay gặp: rerun từ step đầu; tin tên job `es-`/`de-` trên trang tài liệu châu Âu; đẩy lại order mà không kiểm số NERP.

### 6. Phần Tech của fraud, payment mode, ERP config
- **Fraud:** đọc FraudConfig (gắn BaseStore, loại Review hoặc Blacklist) để giải thích vì sao order dừng; order WAIT_FRAUD_MANUAL_CHECK do subsidiary hoặc CS agent duyệt — Tech không duyệt; sửa FraudConfig trên production là data change cần PC.
- **Payment mode:** ngoài 4 check ở G4.1, Tech đọc: Active, Payment Strategy (class chạy flow thanh toán), Payment Response Strategy, Supported Delivery Modes, Payment Provider Parameters. Tạo/sửa payment mode là CFG-02: PC + second check + Tech Lead review.
- **ERP:** mỗi site cần ERP Config (GERPConfig) và ERP FI Config (sold-to, partner number) để gửi order sang NERP; kênh mới thì clone config từ eStore cùng nước qua PC, mức Mandatory + TL (SIT-03, SIT-04). Order kẹt WAITING_FOR_SEND_FINANCIAL: kiểm trước ERP number và mapping payment mode / sold-to.

## Quiz (đáp án)
1 Order ở EXTERNAL_FRAUD_RESULT_PROCESSED, gateway không trả transaction code; trước khi rerun `takePayment` kiểm → **order đã có CAPTURE payment entry chưa**. 2 Khi nào SHIPPED → **khi Hybris nhận 1st GI từ NERP**. 3 Log Kibana cho thấy Hybris đã gửi PO nhưng không có SO trả về, subsidiary đòi đẩy lại → **không đẩy lại; Level 2 mở Maintenance Request**. 4 Order WAIT_FRAUD_MANUAL_CHECK vì địa chỉ khớp Review list → **Tech không duyệt; subsidiary/CS agent xử lý**. 5 Tìm log tạo SO cho order kẹt ORDER_SPLIT → `"<order code>" AND "<soap"` trong index `logs-json-*`. 6 Clawback trade-in cho order 60 ngày trước → **dữ liệu order process bị xóa sau 45 ngày**. 7 Đã map region cho order kẹt ORDER_SPLIT → **PC ticket, rerun từ đúng step đã dừng**.
