# G4.1 Orders: order process, split, consignment, fraud, delivery, refund

> Nguồn: page 2483388671 · 60 phút (Study 20' · Demo 15' · Quiz 8' · Practice 17') · Facilitator giải thích Figure 7 của textbook và mở order thật trên Backoffice staging; facilitator: Tech Sub-Lead + Merch/QA Sub-Lead (phần "phát hiện sớm và báo") · Cần account Backoffice staging SMS (s2) đã test ở PR-G3.2-2; chưa có thì ngồi cùng đồng nghiệp hoặc điền bảng theo màn hình facilitator.

## Mục tiêu
Liệt kê đúng thứ tự các bước chính của order; phân biệt order vs consignment và vì sao status order theo consignment chậm nhất; phân biệt Review vs Blacklist fraud rule và ai quyết định order ở WAIT_FRAUD_MANUAL_CHECK; tính RDD bằng công thức; nhận 5 điểm kẹt phổ biến và biết báo ai.

## Thuật ngữ
**Order**; **Consignment** (một shipment trong order: kho, delivery mode, status, tracking riêng); **Order entry** (dòng order, giữ giá) vs **Consignment entry** (dòng shipment, giữ số lượng giao); **Order process** (chuỗi bước tự động; "stuck" = dừng ở một bước); **ORDER_SPLIT** (status khi Hybris tách consignment; step là `splitOrder`); **WAITING_FOR_SEND_FINANCIAL** (chờ gửi FI đầu tiên sang N-ERP, trước split) vs **WAITING_FOR_FINANCIAL** (N-ERP đã gửi billing number, chờ hoàn tất tài chính trước COMPLETED); **Fraud check**; **Review / Blacklist**; **WAIT_FRAUD_MANUAL_CHECK**; **Delivery mode**; **Payment mode**; **RDD** (requested delivery date, field Requested Time); **CS agent** (nhân viên CSKH phía subsidiary).

## Nội dung
### 1. Order và consignment
Mỗi lần khách đặt hàng Hybris tạo 1 order; hàng ở nhiều kho hoặc cần nhiều delivery mode thì tách thành nhiều consignment (tùy cấu hình nước còn có thể tách theo product division). Điện thoại + tủ lạnh của chị Lan = 1 order, 2 consignment. `PAYMENT_AUTHORIZED` / `PAYMENT_CAPTURED` chỉ thuộc order. Sau khi thu tiền & split, **status order theo consignment chậm nhất**; order chỉ hoàn tất khi consignment cuối xong và financial posting đóng. Giá nằm ở order entry, số lượng giao ở consignment entry; N-ERP tạo 1 Sales Order (SO) cho mỗi consignment.

### 2. Luồng chính
CREATED → PAYMENT_AUTHORIZED (giữ tiền) → fraud check → PAYMENT_CAPTURED (thu tiền) → WAITING_FOR_SEND_FINANCIAL (first FI sang N-ERP) → ORDER_SPLIT (`splitOrder` tạo consignment) → mỗi consignment sang N-ERP: SO (SHIPPING_REQUESTED), Delivery Order (SHIPPING_PREPARATION), first Goods Issue (SHIPPED) → billing number → WAITING_FOR_FINANCIAL → COMPLETED.
- External service (trade-in, SC+, SIM) được kiểm *trước* khi thu tiền, kích hoạt *sau* khi thu tiền. Order 3PD có process riêng (G4.2). Order voucher RNPL trên eStore dùng delivery mode số, không giao từ kho; RNPL 3PD có consignment tự hoàn tất, không gửi N-ERP. Hủy/trả: CS agent hoặc Tech tạo cancel/return trong Hybris → N-ERP tạo return document → refund qua payment gateway.

| Order status | Ý nghĩa | Chứng từ N-ERP |
|---|---|---|
| CREATED | vừa đặt | – |
| PAYMENT_AUTHORIZED | gateway giữ tiền (chỉ order) | – |
| WAIT_FRAUD_MANUAL_CHECK | bị Review rule giữ; subsidiary/CS agent quyết | – |
| PAYMENT_CAPTURED | đã thu tiền (chỉ order) | – |
| WAITING_FOR_SEND_FINANCIAL | chờ gửi FI đầu tiên | First FI |
| ORDER_SPLIT | `splitOrder` tạo consignment | – |
| SHIPPING_REQUESTED | N-ERP trả SO | SO |
| SHIPPING_PREPARATION | N-ERP trả DO | DO |
| SHIPPED | First GI: hàng rời kho | 1st GI |
| WAITING_FOR_FINANCIAL | có billing, chờ hoàn tất tài chính | Billing |
| COMPLETED | đã giao & đóng tài chính | – |
| SUSPENDED | process dừng do lỗi/review; Tech xử lý | – |

### 3. Fraud check
Hybris chạy internal check theo FraudConfig của base store (address, email, phone, IP, discount level) + customer quota + single-use code, sau đó external check. **Review rule** → order tạo ra nhưng vào WAIT_FRAUD_MANUAL_CHECK chờ quyết định tay; **Blacklist rule** → khách không checkout được. Order ở WAIT_FRAUD_MANUAL_CHECK do **subsidiary hoặc CS agent** duyệt/từ chối theo fraud comment — **CoE (kể cả Tech) không duyệt để cứu SLA**.

### 4. Nơi order hay kẹt
Tech sửa; Merch/QA nhận biết và báo sớm. "Rerun from the right step" = chạy tiếp từ bước dừng, không từ đầu. **Trên production mọi rerun hay sửa data order là Tech change cần PC do Oliver Leung duyệt** (CM-13 §9, G2.6); mọi Groovy/ImpEx production có ITGC header dòng 1: `#NOTE ITGC_JIRA:PC-1234(COEC-5678)` (Groovy: `//NOTE ITGC_JIRA:...`); file mới chạy staging trước. Merch/QA báo trên ticket: order code, status hiện tại, nguyên văn lỗi; không đụng vào; không chụp màn hình bằng điện thoại.

| Kẹt ở | Nguyên nhân thường gặp | Ai xử lý |
|---|---|---|
| CREATED quá lâu | system restart/deploy đang chạy | Tech kiểm process, rerun từ đúng bước |
| EXTERNAL_FRAUD_RESULT_PROCESSED | ở `takePayment` gateway không trả transaction ID | Tech hỏi subsidiary đã authorize chưa; nếu rồi, đặt payment transaction entry thành success rồi rerun. **Trước khi rerun `takePayment` kiểm không có CAPTURE entry, kẻo trừ tiền khách 2 lần** |
| WAIT_FRAUD_MANUAL_CHECK | dính Review rule | Subsidiary/CS agent |
| ORDER_SPLIT, "missing values for [warehouse]" | không có tồn ở kho nào dùng được — **ca phổ biến nhất** | Tech check tồn từng kho; subsidiary đẩy tồn; Tech rerun |
| ORDER_SPLIT, lỗi khác | địa chỉ thiếu region code (`getRegion() is null`); store O2O thiếu ship-to code ở N-ERP ("Please input Customer Number"); plant code kho không khớp N-ERP ("Plant XXXX is not defined") | Subsidiary cấp data; Tech bổ sung & rerun |
| PAYMENT_CAPTURED, lỗi `incrementWtVolQtyDailyUsage` | 1 SKU trong order (thường SC+) thiếu delivery mode | Tech thêm delivery mode vào order entry, rerun |
| WAITING_FOR_EXTERNAL_SERVICE_PROCESS | partner trade-in/SC+ không phản hồi, hoặc SC+ trả "INVALID BILL DATA" (sai PID) | Tech xác nhận với partner, sửa data, rerun từ `processExternalServicesAction` |
| SHIPPED lâu | consignment xong nhưng process không đi tiếp, hoặc thiếu billing number | Tech rerun từ `isFullyFulfilled`/`isProcessCompleted`; thiếu billing thì subsidiary cấp trước |
| SUSPENDED | process dừng do lỗi/review | Tech theo order remediation runbook |

### 5. Chọn kho & tính RDD
Hybris lấy kho của site (VN: kho gắn với region của địa chỉ), xếp theo priority (số lớn thắng); kho đầu hết hàng thì thử kho kế; site không có kho thì dùng kho của base store. Chọn kho xong mới tra bảng lead time theo kho + delivery mode.
**RDD = order date + lead time + warehouse operation lead time + 1 (nếu đặt sau cut-off) + ngày không giao + ngày lễ.** Lead time tính ngày lịch; cut-off thường 15:00; warehouse operation lead time mặc định 0; ngày lễ ở Base Store › Administration › publicHolidays. VD: đặt Thứ Tư 16:00, lead time 5, không giao Thứ Bảy/Chủ nhật → 5+1=6 ngày, cộng 2 ngày cuối tuần → Thứ Năm tuần sau.

### 6. Delivery mode & payment mode
Hai thứ liên kết: mỗi delivery mode có danh sách *Supported payment modes*; khách chọn delivery mode thì chỉ thấy payment mode trong danh sách. VD TV giao xe tải chỉ nhận thẻ, điện thoại giao hỏa tốc nhận thẻ/COD → giỏ chung chỉ thanh toán bằng thẻ; hai danh sách không giao nhau thì không mua chung giỏ được.
Khách không thấy payment method → kiểm theo thứ tự: payment mode Active? có ở cấp áp dụng (multistore → website → base store; Site Payment Config ở PH, ID, TH) và cả base store? giỏ đạt mức tối thiểu (trả góp theo ngân hàng & kỳ hạn)? mọi delivery mode trong giỏ có liệt kê nó? Restrict Products có loại sản phẩm trong giỏ? quy tắc nước (VN: `vn-pay-at-shop` chỉ hiện cho store type `CS_STORE`)?

## Quiz (đáp án)
1 Điện thoại + tủ lạnh → **1 order, 2 consignment**. 2 Điện thoại DELIVERED, tủ lạnh SHIPPING_PREPARATION → **chưa xong, theo shipment chậm nhất**. 3 Thứ tự → **authorize → fraud → capture → N-ERP → split**. 4 Review vs Blacklist → **Review chờ duyệt; Blacklist chặn checkout**. 5 Order SG ở WAIT_FRAUD_MANUAL_CHECK 3 giờ → **subsidiary/CS agent quyết theo fraud comment**. 6 O2O TH kẹt ORDER_SPLIT "Please input Customer Number" → **store thiếu ship-to code ở N-ERP**. 7 Đặt Thứ Tư 12/6/2024 16:00, lead 5 ngày, không giao T7/CN, cut-off 15:00 → **Thứ Năm 20/6**. 8 TV (chỉ thẻ) + điện thoại (thẻ/COD) → **chỉ thẻ**.
