## Nội dung
### 1. Backoffice vs HAC
Backoffice là giao diện nghiệp vụ (xem/sửa từng object bằng form). **HAC** là console kỹ thuật: query nhiều dòng, nạp data bằng ImpEx, chạy Groovy; kết quả đã mask PII. **HAC chỉ dành cho Tech**; Merch/QA không có HAC trên cả staging lẫn production (CM-09 §7.1, §7.3) — họ đọc data ở Backoffice, cần nhiều dòng thì nhờ Tech qua linked COEC ticket. Merch/QA vẫn phải đọc được query và ImpEx vì chúng xuất hiện trong ticket, runbook, PC ticket — phải nói được file sẽ đổi gì trước khi chạy.
Menu HAC: Console › FlexibleSearch (đọc data); Console › ImpEx Import (Tech; file mới chạy staging trước; production cần PC duyệt + ITGC header); Console › Scripting Languages/Groovy (Tech; mặc định rollback; **mọi Groovy trên production cần PC duyệt, kể cả read-only và dry run**); Platform › Configuration (xem config đang bật); Platform › Logging and Monitoring (Tech khi điều tra); Platform › Initialization/Update (**không dùng**).
> Ghi chú: textbook ch.07 và khóa này thống nhất HAC chỉ Tech; trang RHQ Impex/Scripting chỉ nói data update mới cần duyệt — **CM-13 thắng**.

### 2. Chọn công cụ & luật trên production
Xem một object → Backoffice. Xem nhiều dòng → FlexibleSearch (Merch/QA nhờ Tech). Thay đổi hàng loạt/cần logic → ImpEx/Groovy của Tech, staging trước rồi PC duyệt cho production. Chạy lại cronjob: Merch/QA không bao giờ; Tech chỉ khi có PC duyệt (TEC-2.3). Initialization/Update: không ai.
Luật production (CM-13 §9.1, §12.1): mọi ImpEx/Groovy cần PC duyệt + ITGC header, **không ngoại lệ cho "chỉ đọc" hay "5 giây"**; FlexibleSearch chỉ đọc để điều tra ticket không cần PC nhưng **ghi lý do lên ticket trước**, chỉ SELECT cột cần; report/data lịch sử/cronjob report mới cần PUMI rồi PC; yêu cầu email khách (EDM) → từ chối mặc định; PII không bao giờ gửi qua email.

### 3. Đọc query từng dòng
Mỗi loại data là một **type** (như bảng), mỗi record là **item** với **pk**. Field trỏ sang object khác (VD status của order) chỉ lưu pk của object đó → muốn đọc code dễ hiểu thì JOIN type kia theo pk.
Query mẫu 3 (một order và status):
- `SELECT {o.code}, {os.code} AS status` — lấy order code & status code, đặt tên cột là status.
- `FROM {Order AS o JOIN OrderStatus AS os ON {os.pk} = {o.status}}` — lấy từ type Order (o) nối type OrderStatus (os) khi pk của os bằng field status của o.
- `WHERE {o.code} = '<ORDER_CODE>' AND {o.originalVersion} IS NULL` — chỉ order đó, chỉ bản hiện hành.
Từ khóa khác: `AND`, `IN ('A','B')`, `LIKE '%stock%'`, `IS NULL`, `ORDER BY … DESC`.

### 4. Bảy luật & năm query mẫu
1. Type và field nằm trong `{ }`. 2. Toàn bộ phần FROM (type + JOIN) nằm trong **một cặp** `{ }` lớn. 3. Field trỏ object khác chỉ lưu pk → JOIN để đọc code. 4. Field nhiều ngôn ngữ cần mã ngôn ngữ: `{p.name[en]}`. 5. Product có một bản cho mỗi catalog & version → luôn lọc catalog + version; order giữ bản cũ khi sửa → thêm `{o.originalVersion} IS NULL`. 6. SKU bán được là type `TokoVariantProduct` (gắn base `TokoProduct`) → tra SKU dùng `TokoVariantProduct`. 7. Tên field trong query có thể khác nhãn màn hình/cột upload (file upload stock ghi `availableAmount`, query dùng `available`); lỗi tên field thì kiểm System › Types.

| Query | Trả lời câu hỏi | Type chính & JOIN |
|---|---|---|
| 1 | SKU có approval & sales status gì, ở catalog/version nào | `TokoVariantProduct`; JOIN ArticleApprovalStatus, LEFT JOIN SalesStatus, JOIN CatalogVersion, Catalog |
| 2 | Tồn SKU từng kho: available, reserved, safety stock, max pre-order | `StockLevel`; JOIN Warehouse |
| 3 | Một order: status, total, thời gian tạo (chỉ bản hiện hành) | `Order`; JOIN OrderStatus |
| 4 | Consignment của một order: status, kho | `Consignment`; JOIN Order, ConsignmentStatus, LEFT JOIN Warehouse |
| 5 | Lần chạy gần nhất & kết quả cronjob stock sync | `CronJob`; LEFT JOIN CronJobStatus, CronJobResult; `LIKE '%stock%'`, ORDER BY endTime DESC |

Query 1: `SELECT {p.code}, {aas.code} AS approval, {ss.code} AS sales_status, {c.id} AS catalog, {cv.version} AS version FROM {TokoVariantProduct AS p JOIN ArticleApprovalStatus AS aas ON {aas.pk} = {p.approvalStatus} LEFT JOIN SalesStatus AS ss ON {ss.pk} = {p.salesStatus} JOIN CatalogVersion AS cv ON {cv.pk} = {p.catalogVersion} JOIN Catalog AS c ON {c.pk} = {cv.catalog}} WHERE {p.code} = '<SKU_CODE>'`
Query 5: `SELECT {cj.code}, {st.code} AS status, {r.code} AS result, {cj.endTime} FROM {CronJob AS cj LEFT JOIN CronJobStatus AS st ON {st.pk} = {cj.status} LEFT JOIN CronJobResult AS r ON {r.pk} = {cj.result}} WHERE {cj.code} LIKE '%stock%' ORDER BY {cj.endTime} DESC`
Lỗi người mới: quên cặp `{ }` lớn trong FROM; dùng `TokoProduct` nên không thấy SKU; không lọc version nên ra nhiều dòng; mở nhầm HAC production vì không kiểm URL.

### 5. Đọc file ImpEx
Ví dụ đặt phí giao hàng cồng kềnh cho SG:
- Dòng 1 `#NOTE ITGC_JIRA:PC-1234(COEC-5678)` = **ITGC header** (PC + COEC gốc); luôn là dòng 1 của file chạy production; Groovy dùng `//` thay `#`. Thiếu hoặc số PC không khớp PC đã duyệt = strike cho người chạy.
- `$siteUid = sg`, `$currency = SGD` = macro dùng lại phía dưới.
- `INSERT_UPDATE ZoneDeliveryModeValue;deliveryMode(code)[unique=true];zone(code)[unique=true];currency(isocode)[unique=true];minimum[unique=true];value` = **ImpEx header** của block: `INSERT_UPDATE` (có thì sửa, chưa có thì tạo; còn INSERT, UPDATE, REMOVE); `ZoneDeliveryModeValue` là type bị đổi; các cột `[unique=true]` cùng nhau định danh dòng; `deliveryMode(code)` tìm delivery mode theo code.
- `;$siteUid-home_delivery_bulky_item;$siteUid;$currency;0.00;0.00` = một data row, bắt đầu bằng `;`, giá trị theo thứ tự cột của header.
Khi đọc file hỏi 4 câu: đổi type nào, mode nào, bao nhiêu data row, cột nào định danh dòng; rồi đối chiếu dòng 1 với PC ticket.
> Ghi chú: khóa này và TEC-2.2 dùng ITGC format `#NOTE ITGC_JIRA:PC-1234(COEC-5678)` như trang RHQ Impex/Scripting; TC-01/TC-05 đề xuất `# PC ticket: PC-XXXX | COEC ticket: COEC-YYYY` — chưa dùng cho tới khi RHQ ban hành format chính thức.
