# MER-P2.3 Coupons and vouchers

> Nguồn: page 2484469822 · 75 phút (Study 20' · Demo 10' · Quiz 10' · Practice 35') · Facilitator: Shift Leader/Sub-Lead · Capabilities C2, C4, C5 · Cần xong MER-2.3 và G1.3 (T1, an ninh thông tin); giả định MER-P2.1. Mang TRN-011 (SCOE-17) và TRN-019 (SCOE-25). TRN-019 có bảng khách (giả) — coi như PII thật: không copy, không tải về máy cá nhân, không dán vào công cụ nào. Truy cập staging Backoffice el3-s2 (Marketing › Coupon Management › Coupons, Promotion Rules, Vouchers), Promotion Simulator, Jira SCOE; Merch không có HAC. Object bắt đầu `TRAINING_<NAME>_TRN011_` hoặc `_TRN019_`. Không bao giờ đính hoặc dán danh sách code; file code ở lại CoE workstation.

## Mục tiêu
Tạo single-code và multi-code coupon với value, total uses, uses per customer đúng, gắn đúng rule; quyết định khi nào batch code phải sang Tech (COEC liên kết + PC ticket) và cách giao code; tính exposure và quyết R3 hay E4; xử lý yêu cầu chứa dữ liệu khách: dừng, báo, trả lời không lặp lại dữ liệu, dựng phương án an toàn.

## Thuật ngữ
**Single-Code Coupon** (một code công khai cho nhiều khách; wizard chỉ hỏi Active và Coupon Code, giới hạn đặt ở editor sau Finish; Name và Start/End để trống trừ khi brief cần); **Multi-Code Coupon** (batch code duy nhất từ prefix, sinh bằng "Number of coupon codes to generate" + Generate); **EmailRestrictedMultiCodeCoupon** (mỗi email một code, chỉ email đó dùng được; tạo bằng "Upload Email and Generate Coupons" từ file một cột email); **Maximum Total / per Customer Redemptions** (`maxTotalRedemptions`, `maxRedemptionsPerCustomer`; trống = không giới hạn, PS-08 chặn với single-code; multi-code không cần giới hạn vì mỗi code dùng một lần, số code là cap); **Coupon Code Generation Configuration** (format code; mỗi market có `MULTI_CODE_CONFIG_<CC>`: phân cách "-", 3 phần × 4 ký tự sau prefix 4 ký tự, VD `CEOD-5BM9-9GML-GCNK`; luôn chọn cái có sẵn, không tạo/sửa); **Coupon exposure** (value × total uses; ≥10,000 USD là E4; TRN-011: 30 × 12,000 PHP = 360,000 PHP ≈ 6,200 USD: R3, không E4); **Delivery record** (cái ghi lên ticket thay cho code: số lượng, prefix, batch, tên file, kênh, giờ); **PII** (dữ liệu nhận diện người; không dán vào comment, không gửi email từ Hybris).

## Nội dung
### 1. Runbook MER-CPN-01
Service Merch lớn nhất: 1,918 ticket trong 2026, ~202/tháng (nhiều nhất PH, MY, VN). Bản thân code là **standard change**; Knox áp cho **rule đứng sau code** (MER-CPN-02, action line riêng trong cùng ticket). Checker: QA team, bắt buộc. Duyệt: Shift Leader, rồi approver Knox của rule. Normal change có Sub-Lead duyệt cho migration và ImpEx load; E4 khi value × total uses ≥10,000 USD. Từ 1/5/2026 mọi promotion mới dùng **coupon**; voucher serial/promotional chỉ còn cho RNPL và legacy. Brief ghi "voucher" thì kiểm object nào.
**V1 single public code:** (1) code còn trống — Coupons › "Type to search" ra "No entries"; thêm Marketing › Vouchers và tìm Jira. Một pool code phục vụ mọi nước; code đã tồn tại ở đâu cũng xin code khác; (2) tạo — Choose Type › Single-Code Coupon; rồi title, cả hai redemption limit, Hide in My Voucher Page True. Name để trống trừ khi brief cho text hiển thị cho khách (hiện trong cart; không bao giờ là số ticket). Start/End để trống để coupon theo ngày của rule, trừ khi brief cần cửa sổ hẹp hơn / Checker: value, total uses, uses per customer đều điền (blocking); (3) internal check — code, value, window kèm zone, site, stacking, giới hạn; (4) link rule — condition "Coupon code" (`y_qualifying_coupons`); không để condition coupon trống (trống thì nhận mọi code); đổi condition rule đã publish cần Knox lại. Loại trừ SKU MX SC+ (SMC) và RNPL e-voucher: không bao giờ có discount; (5) test restriction — đặt `testusergroup` vào condition target-customer của rule để chỉ tester kích hoạt; giữ Hide in My Voucher Page True. Restriction của coupon (user group, customer, email; không bao giờ sửa email hash) chỉ đặt khi brief giới hạn đối tượng; nó ở lại sau go-live và phải khớp condition customer của rule; (6) tự simulate — giỏ đủ điều kiện; dưới mức chi tối thiểu; SKU loại trừ; từng cặp stacking; lần dùng thứ hai của cùng khách / QA: SIM trước start và sau end; lần hai bị từ chối; (7) QA, duyệt, Knox — QA REVIEW; Shift Leader; gỡ `testusergroup` khỏi rule (restriction brief yêu cầu giữ), điền Approval section, publish; ghi reference và đường trong comment; (8) go-live — rule PUBLISHED trong ~90' sau duyệt (hai job Knox chạy mỗi 45' trên production; hằng giờ :02, :12 trên el3-s2); áp code trên một site mỗi kênh.
Known error: KE-MER-CPN-01-01 code "not valid" sau go-live (kiểm theo thứ tự: restriction còn, Knox pending, thiếu site, coupon inactive, sai time zone); KE-04 rule sửa sau duyệt (version mới, Knox lại); KE-06 voucher dừng ở ngày cũ (chỉ gia hạn coupon hoặc chỉ rule: gia hạn cả hai).
> Priority mặc định Low (24h) và Medium (16h) khi ticket là một promotion, mức RHQ thống nhất ở handover 23/10 (header MER-CPN-01). TRN-011 và TRN-019 giữ Medium của requester kèm lý do. Cách đếm nhiều rule trong một ticket coupon là D13 under review.

### 2. Single-code và multi-code
**Single-code (V1).** Coupons › "+" (**Choose Type**) › **Single-Code Coupon**. Wizard chỉ hỏi Active và Coupon Code (chữ hoa). Sau **Finish** mở editor: tab Coupon Configuration › title (localised); Name trống trừ khi brief có text hiển thị cho khách; Coupon Validity › Start/End Date trống để ngày rule áp dụng (chỉ điền cho cửa sổ hẹp hơn trong kỳ rule), **Maximum Total Redemptions**, **Maximum Redemptions per Customer**; tab Administration › Hide in My Voucher Page (mặc định True). Một order là một lần dùng.
**Multi-code (V2).** Choose Type › **Multi-Code Coupon**. Wizard yêu cầu Coupon Code Generation Configuration, Coupon code seed number (điền sẵn), Active và Coupon Prefix. Sau Finish: Generated Coupon Codes › "Number of coupon codes to generate" › **Generate**; job `TokoGenerateVoucherCodesCronJob` ghi file code. Kiểm số lượng bằng `couponCodeNumber` (generatedQuantity trống trên staging). Kiểm prefix chưa dùng (tìm trong Coupons, Vouchers, Jira). Prefix 4 chữ hoa hoặc số, không đổi được sau khi sinh. Multi-code không cần redemption limit. Không giữ code để dùng sau.
**TRN-011 (PH B2B):** requester xin "serial voucher codes, prefix 3 chữ như lần trước". Vi phạm Coupon Guidelines nên Doer dựng **multi-code coupon** và nói trong ghi nhận; đó là luật RHQ, không phải câu hỏi cho subsidiary. Setting: 30 code, 1 lần/code, prefix `ARCT` trên production (`TRAINING_<NAME>_TRN011_CPN01` trong lab), 16/11/2026 00:00 → 16/12/2026 23:59:59 giờ PH (GMT+8), Hide in My Voucher Page TRUE, restriction baseSites = `phtest1`. Ba rule, mỗi discount một rule: `SM-S931BLBCPHL` 5,000 PHP, `SM-S948BZVCPHL` 12,000 PHP, `SM-S938BAKCPHL` 8,000 PHP, mỗi rule có condition coupon, Website = default promotion group của `phtest1`, publish vào preview module. Simulator (đồng hồ GMT+8 trùng giờ PH nên không đổi; VN, TH cộng một giờ): S931 + coupon → −5,000; S948 + coupon → −12,000; S931 không coupon → không; SKU khác + coupon → không; D+31 → không; dùng lần hai → từ chối.
> Dùng `MULTI_CODE_CONFIG_<CC>` của market (VN, MY, SG, TH, PH, ID, NZ…): prefix 4 ký tự rồi 3 phần × 4 ký tự với "-". Vài config cũ trên staging có 4 phần; không dùng, và không bao giờ tạo/sửa config dùng chung (MER-CPN-01 §2.1).

### 3. Giới hạn sinh code và xử lý code: khi nào Tech phải giúp
Merch sinh code ở Backoffice tới **1 triệu code** mỗi lần, trong vài phút (KB Coupon; SDSAP demo live 29/10). 500,000 trong CM-13 chỉ là ví dụ. Trên 1 triệu, hoặc migration, hoặc ImpEx load: Tech chạy ImpEx qua **COEC liên kết + PC ticket**, ticket Merch chờ ở ON HOLD COE (clock vẫn chạy nên báo sớm). Merch cũng không tạo được customer group: đó cũng là COEC; Merch chỉ thêm khách QA vào group có sẵn. Khi Tech sinh batch, Merch PIC kiểm: số lượng bằng brief; code đầu, cuối và một code ngẫu nhiên đúng format và chưa dùng (QCL-CPN-01 mục 8).
KT Samsung (21/10): *Merch cần một phần việc từ Tech (VD sinh nửa triệu voucher code): giữ ticket Merch, tạo COEC mới liên kết bằng issue link, chuyển ticket Merch sang On Hold COE kèm comment. Hai SLA chạy song song: mỗi ngày Tech dùng cũng tính vào Merch.*
Quy tắc xử lý code (code là dữ liệu có giá trị): code duy nhất, batch credit, VOC code chỉ rời Hybris qua kênh RHQ duyệt, trong file có mật khẩu, mật khẩu gửi riêng; không bao giờ đính Jira, email, chat hay AI. Ticket chỉ có delivery record. Người giao file không phải người duyệt giá trị. Code giao cho chủ account của subsidiary, không trực tiếp cho công ty đối tác. QA evidence chỉ cho thấy cấu hình và một hai kết quả test mẫu, không bao giờ danh sách code.
> Kênh giao file code và email list là D8 under review. Tới đó: không dán code hay email vào comment hoặc attachment trên ticket.

### 4. Bẫy PII: yêu cầu kèm danh sách khách
**TRN-019 (MY):** requester muốn coupon RM300 cho 12 khách VIP, dán tên, email, mobile vào description, đính Excel không mật khẩu, nhờ CoE "email trực tiếp code cho từng khách" và "dán danh sách code vào ticket này". Thứ tự đúng:
1. **Initial response** trước: APPROVED-ES → STG SETUP.
2. **Dừng.** Không copy bảng, không tải file về máy cá nhân, không trích trong comment, không đưa vào chat hay AI để "lọc email".
3. **Báo Shift Leader ngay.** Shift Leader quyết báo DevSecOps hay RHQ; CoE không tự sửa description của requester.
4. **Một comment không có dữ liệu khách:** yêu cầu requester xóa bảng và attachment, gửi danh sách email một cột trong file có mật khẩu qua kênh được duyệt, mật khẩu riêng. Nói rõ CoE không liên hệ khách cuối và không đăng code lên ticket. ON HOLD SUBS, subsidiary là Assignee.
5. **Sau khi có danh sách sạch:** dựng **EmailRestrictedMultiCodeCoupon** (upload file email **một lần**: upload lần hai sinh bộ code thứ hai), cả hai redemption limit = 1, rule RM300 trên `SM-S948BLBQXME` và `SM-S948BLBCXME` ở `my`, và gửi code list chỉ cho reporter trong file có mật khẩu.
Code hay danh sách khách đã rời kênh được duyệt = security incident (MER-INC-01, High): theo 5 bước giờ đầu (dừng, giữ nguyên, báo miệng ngay, báo cáo viết trong 1 giờ, làm theo chỉ dẫn), và không bao giờ chụp hay chuyển tiếp dữ liệu bị lộ "làm evidence".
